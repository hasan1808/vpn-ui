vpn-ui redesign / sheet set 06

The inbound form

Five ways to rebuild Add and Edit Inbound, drawn over the surface as it was measured out of web/html/form/: 24 protocols whose forms range from 23 fields to 195, all of them rendering today into the same 520px column with no sections.

Every scheme below renders from one fixture file, so they can be compared like for like. Switch the protocol and the mode with the controls that follow sheet 00.

00

The surface being redesigned

Counted, not estimated. Every number is a-form-item occurrences in the partials a protocol can reach.

Reachable field count means every toggle expanded and one entry in each repeater. It is not what you see at rest, it is what the dialog can grow to while you work in it. The eight Xray-native protocols are large because transport, socket options, final mask, TLS and sniffing all stack on top of the protocol form. The other sixteen carry no stream at all.

  • One column, no width. The modal sets no :width, so every protocol renders into ant's default 520px with an 8/14 label split. A 195-field form and a 23-field form get the same container.
  • Add and Edit are different tasks. The protocol select is :disabled="isEdit". On Add it is the one control that rewrites everything below it, because setting the protocol replaces settings and stream wholesale. On Edit it can never change.
  • The save gate is silent. modalFormValid disables the OK button with no message: a missing certificate on OpenVPN, OpenConnect, SSTP or IKEv2, or any of the eight distinct causes inside XHTTP's hasCoreConfigProblem(). The operator sees a dead button and no reason.
  • Some blocks repeat, and that is the opening. The same commerce block is on all 24 protocols, the same network handout on 9, the same device cap on 8, the same reachability row on 11, and the same Content / File / Managed certificate switch on 4. Today each is re-declared per partial and drawn as an undifferentiated run of rows.
  • Sniffing renders for everything. Its collapse panel sits outside every v-if in form/inbound.html, so a PPTP or GRE inbound offers a sniffing panel that means nothing for it.

01

Ledger

One scroll, but ruled into named sections with a running index.

The smallest change that fixes the worst symptom. The stack stays a stack, so nothing about field order or conditional rendering has to move, but every run of rows gets a heading, a count, and an entry in an index that tracks position. Advanced groups arrive folded, stating what is inside them.

640pxup from 520

Cost: the cheapest of the five. It is a wrapper plus headings around the existing partials, and the index is derived from those headings. It does not reduce the 195 fields, it makes them countable and navigable. If the answer has to ship in one pass, this is it.

02

Rail

Sections on the left, one section at a time on the right.

The same vocabulary the section tree already brought to Settings and Xray, applied to the form. The rail carries per-section state: a red dot for a section holding the reason Save is disabled, a filled dot for one the operator has visited. Only one section is in the viewport at a time, so the 195-field case never renders as a wall.

960pxclick a section

Cost: the section list has to be authored per protocol, which is 24 small maps rather than one. In exchange it is the only scheme where a small protocol and a huge one feel the same, and it inherits the nav idiom the panel already shipped. Watch SSH: four sections, one of which holds two fields.

03

Stepper

Add is a sequence. Edit is the same sequence, unlocked.

Built around the fact that picking a protocol discards everything below it. Making that choice step one costs nothing, because on step one there is nothing to lose. The steps are generated from what the protocol actually has, so SSH gets three and VLESS six, and the last step is a review that states what will be created and what is blocking it.

720pxclick a step

Cost: best first-run experience of the five and the worst for routine editing, where a wizard stands between the operator and one field. It needs the Edit path to open unlocked on the section that was clicked, or it becomes an obstacle. The protocol picker with families is worth stealing on its own, whichever container wins.

04

Bento

Every concern a card, sized by weight, all on screen.

The direction the rest of the redesign is already on, applied here: no navigation at all, a mosaic where a card's span reflects how much it carries. Editing one field means finding one card, and the heavy cards stay stubs until opened, which is what keeps a 195-field protocol on one screen.

1040pxno navigation

Cost: excellent for scanning an existing inbound, weakest for a first add, where a mosaic gives no order to work through. Card spans have to be authored per protocol or the grid tears. And it does not actually fit: laid out uncapped, VLESS measures 1641px of card height at 1040px wide, so even the widest scheme scrolls on the protocols that most needed the space. The grid above is capped at 560px to show what that really looks like.

05

Split

Form on the left, what it produces on the right.

The only scheme that answers fact 03 by construction. The right pane holds three things that exist today only after saving: the listener the server will actually run, the artifact the customer receives, and a ledger naming every reason Save is disabled, each pointing at the field that caused it. Warnings that arrive late, like the IKEv2 iOS certificate check, land here too.

1040pxlive outcome pane

Cost: the outcome pane is new work with a real backend seam. The share link and the .ovpn are generated in two places already (the JS model and Go), and a preview that drifts from what saving produces is worse than no preview. The validation ledger alone, though, is portable to any of the other four.

If you want a recommendation: 02 Rail as the container, with 05's validation ledger docked in its footer and 03's family protocol picker used as the Add entry point. Rail matches the section tree that just shipped, so the panel gains one navigation idiom instead of a second one. The ledger is the part that fixes a real defect rather than a layout complaint, and it is portable, so it can land first and independently. 04 Bento is the one to pick instead if editing an existing inbound is the common case rather than creating one.

What none of these solve: the field count itself. Sniffing on a PPTP inbound, 64 final-mask fields behind a stream protocol nobody masks, and 18 socket options on every one of the eight Xray protocols are content problems, not layout problems. A container makes them navigable. Deciding that an inbound should not offer them is a separate and more valuable piece of work.
