Five ways to list inbounds

The same thirteen inbounds, five information architectures. Everything is drawn in the panel's own tokens, so what you are choosing between is the structure, not the paint. The fixture is deliberately awkward: one inbound whose blank certificate makes Xray refuse the whole configuration, one that can never be metered, one that binds no port at all, one over quota and one expiring this week. A scheme that cannot say those things out loud is not ready. Pick one and it gets built; pick two and I will graft the better half of the loser onto the winner.

Optimised for
Continuity. The table people already know, with the tag soup removed.
The change
Ten columns become five. Remark, port, protocol, network and security collapse into one identity cell; the five account popovers become one segmented bar.
Costs
Cheapest by far. A column array and a slot rewrite. Drag reorder, select-all and pagination all survive untouched. But it is still a table, and nothing about it is memorable.

Optimised for
Knowing what serves what. This box runs five daemons; the flat table hides which one owns which row.
The change
Inbounds group into bands by the process that carries them, and each band header states whether that process is up. When charon dies you can see exactly which rows went dark.
Costs
Reordering gets awkward. SortOrder is one global sequence, so drag inside a band has to map back to global positions. Needs the per-core state the Overview already fetches.

Optimised for
Density. A server with forty inbounds, read the way you read ss -tulpn.
The change
Monospace, port first, fixed columns, one line per inbound, and a live throughput trace per row so a dead listener is visible without opening anything.
Costs
The trace does not exist yet. The API returns cumulative counters only; per-inbound rate means either client-side differencing across polls or a new sampling endpoint. Also the least friendly of the five to a first-time operator.

Optimised for
Small fleets and phones. Ten or fifteen inbounds you know by name, each with its actions in reach.
The change
No table at all. One card per inbound, actions on the card rather than behind a menu, and the grid reflows to one column on a phone with no separate mobile layout.
Costs
Highest. Drag reorder, select-all, pagination and column sorting all have to be reinvented outside the table. Falls apart past roughly thirty inbounds. In exchange the isMobile column fork disappears.

Optimised for
Walking up to the panel cold. The page opens on what is wrong, in a sentence, with the button that fixes it.
The change
Anything broken, depleted, expiring or switched off is promoted to the top with a plain-English diagnosis. Everything healthy collapses to one quiet line each.
Costs
Needs a health model the panel does not have. Today there is only an enable flag; "the core refused this" is not stored anywhere. Backend work to capture the config-test failure per inbound is the price of the whole idea.
